# 프로젝트 생성 템플릿 — 작업 방법론

작업지시자(사람)와 AI 에이전트가 함께 일하는 프로젝트의 **운용 규칙 한 벌**을 담은 템플릿이다. 코드는 없다 — 규칙 문서와 폴더 골격뿐이다.

핵심은 하나다. **사람은 생각·결정, AI는 실행.** 나머지 규칙은 전부 이 분담이 실제로 지켜지도록 만드는 장치다.

---

## 1. 권위 구조 — 먼저 이것부터

문서는 셋뿐이고, 권위는 주제별로 정해진다.

| 문서 | 담는 것 | 그 주제의 권위 |
|---|---|---|
| `docs/manual/working_protocol.md` | **작업 방법론** — 프로젝트가 바뀌어도 그대로인 규칙 | **정본** |
| `AGENTS.md` | ① 방법론의 **작동 발췌본**(규칙·절차만) ② **프로젝트 고유 정보** | ①은 발췌, **②는 정본** |
| `CLAUDE.md` | `@AGENTS.md` 한 줄 | — |

무엇을 어디에 쓰는지는 이렇게 갈린다. **분담은 대칭이 아니다** — 작동본은 보편·고유를 모두 담고, 한쪽을 비우는 것은 정본뿐이다.

|  | 정본 | 작동본 |
|---|---|---|
| **프로젝트 보편 규칙** | 전문 + 취지·논증 | 행동을 규율하는 부분만 발췌 |
| **프로젝트 고유 규칙** | **두지 않는다** | **여기가 유일한 자리** |

덕분에 **프로젝트를 시작할 때 채울 곳이 `AGENTS.md` 한 파일로 모인다.** 고유 항목이 여러 문서에 흩어져 있으면 프로젝트마다 그 전부를 손봐야 하고, 빠뜨린 한 곳이 곧 어긋난 규칙이 된다.

규칙을 고칠 때는 정본을 먼저 고치고, `AGENTS.md`의 해당 발췌를 같은 커밋에서 맞춘다. 발췌를 먼저 고치면 정본이 거짓이 된다.

**주제별 발췌본은 두지 않는다.** 정본의 한 절을 다시 요약한 문서는 읽을 사람이 따로 없으면서 동기화 의무만 늘린다.

## 2. 쓰는 법

1. **복제한다.** 추적 중인 파일만 내보내므로 작업 중이던 잡파일이 따라가지 않는다. 첫 커밋이 복제 시점 상태를 고정하며, 나중에 규칙을 템플릿으로 올릴 때 그 커밋이 비교 기준이 된다(규약 §6).

   ```sh
   mkdir -p ~/Workspace/<프로젝트>
   cd <이 템플릿> && git archive HEAD | tar -x -C ~/Workspace/<프로젝트>
   cd ~/Workspace/<프로젝트> && git init -b main && git add -A && git commit -m "템플릿에서 복제"
   git branch devel
   ```

2. **`AGENTS.md` §1과 §2를 채운다.** 채울 곳은 아래 §3에 있고, 이 검색으로 전부 나온다.

   ```sh
   grep -rn '기입' . --include='*.md'
   ```

3. 쓰지 않을 것을 **지운다** — 빈 자리 예약을 방치하면 규칙 문서가 읽히지 않는 문서가 된다.
   - 방법론 학습 교재를 병행하지 않는다면 `AGENTS.md` §6 전체 (지워도 규약 §6의 규칙 갱신 경로는 남는다)
   - 독자 분류가 필요 없다면 `docs/design/`·`docs/domain/`
   - 금지선·도메인 특수 항목이 없다면 `AGENTS.md` §2 ⑦⑧과 그 아래 두 절
4. 이 `README.md`를 프로젝트 자신의 README로 교체한다(규약 §11 모듈 B). 템플릿 안내는 프로젝트 문서가 아니다.
5. 첫 `docs/orders/yyyymmdd.md`를 열고 시작한다.

## 3. 채울 곳

거의 전부 `AGENTS.md` 안에 있다.

**개시 시 반드시 채우는 것**

| 위치 | 내용 |
|---|---|
| `AGENTS.md` §1 목표와 요구사항 | 무엇을 만드는가, 요구사항, 일반화 금지선 |
| `AGENTS.md` §1 아키텍처·기술 스택 | 확정 스택과 범위 전제. 미확정이면 그렇게 쓴다 |
| `AGENTS.md` §1 현재 상태 | 현재 로드맵 단계, 현재 가동 마일스톤 — 진행에 따라 갱신한다 |
| `AGENTS.md` §1 빌드·실행과 자동 검증 | 명령 목록. **각 루프의 「자동 검증」이 무슨 명령인지** — 이게 비면 루프가 작동하지 않는다 |
| `AGENTS.md` §1 원격 저장소와 공개 범위 | 원격 경로, private/public, 프로젝트 고유 Git 규칙 |
| `docs/manual/roadmap.md` | 마일스톤 목록, 운용 제약 |
| `.gitignore` | 스택별 무시 규칙 |

**해당하는 경우에만**

| 위치 | 내용 |
|---|---|
| `AGENTS.md` §2 ⑦ + 「금지선」 | 애초에 하지 않을 일과 그 상세 |
| `AGENTS.md` §2 ⑧ + 「도메인 특수 항목」 | **AI가 준비까지만 하고 최종 판정은 사람이 하는 대상** |
| `AGENTS.md` §2 마지막 문단 | 커밋·push의 상설 승인 예외 |
| `AGENTS.md` §6 | 교재를 병행하는 경우의 교재 저장소 경로·학습할 장·설치 상태 |

### 〔기입〕과 자리 예약은 다르다

인용문으로 표시된 절은 **자리 예약** — 아직 정하지 않은 규칙의 설치 위치를 미리 잡아 둔 것이다. 개시 시 채우지 않고, 그 규칙이 필요해질 때 본문으로 교체한다. 규약 §8 일부·§9(피드백)·§10(릴리스)가 여기 해당하며, 모두 정본에만 있다.

자리 예약은 정본·작동본 어느 쪽에도 둘 수 있다 — 보편·고유 분담의 예외다(규약 §0). 정본과 작동본이 각자 자기 것을 갖고, 별도 대장을 두지 않는다.

```text
.
├── AGENTS.md                       작동 발췌본 + 프로젝트 고유 정보 (매 세션 로드)
├── CLAUDE.md                       @AGENTS.md 한 줄
├── README.md                       이 파일 — 프로젝트 개시 시 교체
├── .markdownlint.jsonc             문서 형식 규칙 (추적 대상)
└── docs/
    ├── document_map.md             문서가 어디 있는가
    ├── manual/
    │   ├── working_protocol.md     ★ 작업 방법론의 단일 정본
    │   └── roadmap.md              마일스톤 목록·운용 제약의 정본
    ├── orders/                     오늘 할 일 (yyyymmdd.md)
    ├── plans/                      작업·실행계획서
    ├── working/                    단계별 완료보고서
    ├── report/                     최종 결과보고서
    ├── feedback/                   사람의 검토·교정 기록
    ├── tech/                       기술적 발견
    ├── troubleshootings/           문제·해결 경험담
    ├── design/                     설계 문서 (선택)
    └── domain/                     도메인 지식 자료 (선택)
```

## 5. 방법론 요약

읽기 전에 알아 두면 정본이 빨리 읽히는 다섯 가지.

- **세 작업 루프** — 타스크를 **복잡도**로 가른다. 지표는 "착수 시점에 답을 모르는 질문의 수". 미지가 많으면 중량(계획서 2종 + 단계별 승인), 적으면 일반(계획서 1종), 없으면 경량(계획서 없음). 애매하면 상위가 기본값이고, 승격은 AI가 그 자리에서, 강등은 작업지시자만 한다.
- **승인 목록은 루프와 무관하다** — 루프는 문서와 관문의 밀도를 정할 뿐, 승인이 필요한 일을 면제해 주지 않는다. 한 줄짜리 경량 작업이라도 승인 항목에 걸리면 그 항목의 관문이 붙는다.
- **마감 2관문** — 로컬과 원격의 경계에서 한 번만 자른다. 마감 승인(커밋 → `devel` 통합 → 회귀 검증)과 반영 승인(push → 확인 → Issue 종료 → 브랜치 삭제). 세 루프에서 동일하다.
- **결정은 옮겨 적지 않는다** — 새 설계 결정은 그 결정을 낳은 타스크의 산출물(orders·계획서·최종 결과보고서)에 남긴다. 별도 결정 로그를 두면 기록과 맥락이 갈라지고 두 벌을 동기화할 의무가 생긴다.
- **개선은 템플릿에 반영한다** — 프로젝트에서 규칙을 고쳐 써 보고 잘 되면, 고유 부분을 벗겨 **일반화해 템플릿에 올린다**(규약 §6). 반영하지 않으면 그 개선은 그 프로젝트와 함께 사라진다. 방향은 단방향이며, 계기는 무엇이든 무방하다.

## 6. 출처

`slp-narrative-generator` 프로젝트에서 rhwp의 Hyper-Waterfall 방법론을 번안해 운용하며 축적한 규칙 체계를, 도메인 고유 내용을 걷어내고 템플릿으로 재구성한 것이다. 그 방법론을 가르치는 교재는 `rhwp-textbook` 저장소에 따로 있다 — 교재는 학습자를 따라다니는 자산이므로 프로젝트에 속하지 않는다.
