# PyTorch 스택을 도입할 것인가

- **작성일**: 2026-08-23
- **작성자**: Claude Opus 5
- **근거**: 실측 (설치 검증) · 문헌 (성능·라이선스)

프로젝트 개시 시 스택을 numpy 전용으로 정하면서 **「이 결정은 v0.1 결과에 따라 재검토
대상」**이라는 단서를 달았다(`AGENTS.md` §1 범위 전제). 첫 실전 실패로 그 조건이 충족되어
재검토했다.

## 1. 도입 가능성 — 걸림돌은 없다

| 항목 | 확인 결과 |
|---|---|
| Python 3.14 지원 | torch 2.13.0, pyannote.audio 4.0.7 모두 cp314 wheel 존재 |
| Apple Silicon | `torch.backends.mps.is_available() == True` (M4) |
| 설치 규모 | 약 90개 패키지, **1.1GB** (별도 venv에 실제 설치해 확인) |
| pyannote community-1 | CC-BY-4.0, 완전 오프라인 실행 가능 |
| 보고 성능 | DER 11.2(VoxConverse) · 11.7(AliMeeting) |
| 접근 제약 | **HF gated** — 계정 동의 후 토큰 필요 |

기술적으로 못 할 이유는 없다. 성능 수치도 매력적이다.

## 2. 그런데 도입 근거가 없다

`003#01`의 실측이 결정적이다. PyTorch 스택의 대표 화자 임베딩(ECAPA-TDNN)을 실제로 설치해
우리 데이터에 돌렸더니 **현행 numpy 구현보다 나빴다** — 길이 초과분 +5.6%p → +19.7%p,
무리 분리도 0.866 → 0.399.

`003#02`의 문헌이 그 이유를 설명한다. 짧은 발화에서 화자 표현이 어휘 내용에 오염되는 것은
구조적 한계이고, 임상·아동 벤치마크에서 최고 시스템도 DER 18~26%이며, 기성 파이프라인을
조율 없이 쓰면 64~73%다.

즉 **「무거운 스택을 들이면 해결된다」는 기대가 실측과 문헌 양쪽에서 부정됐다.**

## 3. 대안 경로는 numpy 안에 있다

`003#03`의 임상가 참조 마이크 방식은 채널 간 에너지비와 상호상관으로 구현되며 **딥러닝이
필요 없다.** 현행 스택 범위 안이다.

`004`의 등급 분류도 마찬가지다. 이미 쓰고 있는 Silero(whisper.cpp 내장, C++ 바이너리)와
음향 특징으로 충분하다.

## 4. 비용

1.1GB 설치, 의존성 90개, 실행 환경 복잡도 상승, 유지 부담. 임상 현장 배포를 염두에 두면
(`001#07`의 제품 정의) 이 무게는 그 자체로 비용이다.

## 유보 — 무엇이 이 결론을 뒤집는가

- **pyannote community-1 실측.** ECAPA는 임베딩 모델 하나일 뿐이고, pyannote는 분할·클러스터링·
  중첩 처리를 함께 설계한 파이프라인이다. 아직 시험하지 못했다(HF 토큰 필요).
- **정답 라벨 확보 후의 재비교.** 지금 비교는 전부 프록시 지표다.

이 둘이 갖춰지고 pyannote가 명확히 우세하면 결론은 바뀔 수 있다.

## 주장

1. PyTorch 스택 도입을 **지금은 하지 말아야** 한다 — 실측과 문헌 어느 쪽도 근거를 주지 않는다.
2. v0.1의 개선은 **numpy 범위 안에서 하여야** 한다 — 참조 마이크·등급 분류 모두 그 안에서 된다.
3. pyannote 실측은 **정답 라벨 확보 후에 하여야** 하며, 그 결과가 나오기 전에는 스택 결정을 다시 열지 말아야 한다.
