# 작업 규약

> 작업지시자(사람)와 AI 에이전트가 **무엇을 누가 하고, 어디서 멈추는가**를 정한 운용 규칙.
> 본 문서는 **작업 방법론의 단일 정본**이다 — 프로젝트가 바뀌어도 그대로인 규칙만 담는다. 방법론 규칙이 서로 어긋나면 본 문서가 우선한다.
> **프로젝트 고유 정보는 본 문서에 쓰지 않는다** — `AGENTS.md`가 그 자리다(§0).
> 인용문으로 표시된 절은 자리 예약이며, 해당 규칙을 정할 때 본문으로 교체한다.

---

## 0. 이 규약의 권위 구조

### 어느 문서가 무엇을 담는가

| 문서 | 담는 것 | 그 주제의 권위 |
|---|---|---|
| `docs/manual/working_protocol.md` | **작업 방법론** — 규칙의 전문과 그 취지·논증·적용 맥락 | **정본** |
| `AGENTS.md` | ① 정본에서 행동을 직접 규율하는 규칙·절차만 뽑은 **작동 발췌본** ② 이 프로젝트에 **고유한 정보** | ①은 발췌본, **②는 정본** |
| `CLAUDE.md` | 규칙을 담지 않는다 — `AGENTS.md`를 Claude Code 컨텍스트로 불러오는 한 줄 어댑터 | — |

권위는 주제별로 정해진다. 방법론 규칙이 어긋나면 본 문서가 우선하고, 프로젝트 고유 정보는 `AGENTS.md`가 유일한 출처다.

### 무엇을 어디에 쓰는가

|  | 정본 | 작동본 |
|---|---|---|
| **프로젝트 보편 규칙** | 전문 + 취지·논증·적용 맥락 | 행동을 직접 규율하는 부분만 발췌 |
| **프로젝트 고유 규칙** | **두지 않는다** | **여기가 유일한 자리** |

- 보편: 세 작업 루프, 승인 관문, 브랜치 3층 구조, 문서 폴더·명명 규칙
- 고유: 기술 스택, 현재 마일스톤, 자동 검증 명령, 도메인 특수 항목, 금지선, 원격 저장소와 공개 범위

분담은 대칭이 아니다 — 작동본은 둘 다 담고, 한쪽을 비우는 것은 정본뿐이다. 정본이 고유 규칙을 비우는 이유는 수정 편의다. 자주 바뀌는 것을 드물게 개정할 문서에 섞지 않고, 프로젝트 개시 시 고칠 파일을 하나로 모은다. 한시적으로만 필요한 규칙도 같은 이유로 작동본에 둔다 — 없앨 때 절 하나만 지우면 된다.

### 두 가지 빈자리 — 분담의 예외

| 표시 | 뜻 | 채워지는 때 |
|---|---|---|
| 인용문 절 — **자리 예약** | 아직 정하지 않은 규칙의 설치 위치 | 그 규칙을 정할 때 본문으로 교체 |
| **〔기입〕** | 프로젝트마다 내용이 다른 자리 | 프로젝트 개시 시 |

정본과 작동본이 각자 자기 빈자리를 갖는다. 어느 쪽에 둘지는 규칙이 정해진 뒤에야 판정할 수 있으므로 예약 단계에서 가르지 않는다. 별도 대장을 두지 않는다.

### 이 구조를 지탱하는 규칙

1. **방법론 규칙의 신설·개정은 정본에서 한다.** 작동본을 먼저 고치지 않는다.
2. **정본의 한 절을 고치면 작동본의 해당 발췌를 같은 커밋에서 맞춘다.**
3. **작동본에는 취지·논증·경위를 싣지 않는다.** 정본은 전체가 발효 중이며, 발췌본이 규칙·절차만 담는 것은 발효 범위가 아니라 서술의 종류를 가린 것이다. 작동본은 매 세션 컨텍스트에 로드되므로 분량이 곧 비용이다. 자리 예약은 최소한으로 둘 수 있다.
4. **주제별 발췌본을 만들지 않는다.** 정본의 한 절을 다시 요약한 문서는 읽을 사람이 따로 없으면서 동기화 의무만 늘린다.

## 1. 역할 분담

원칙은 하나다 — **사람은 생각·결정, AI는 실행.**

### 작업지시자 (사람) — 생각·결정

- **방향 설정**: 다음에 무엇을 만들까
- **우선순위**: 무엇이 더 중요한가
- **품질 판단**: 충분히 좋은가
- **아키텍처 결정**: 이 구조가 옳은가
- **★도메인 지식**: 이 결과물이 이 분야에서 옳은가 — 대체 불가 핵심
- **피드백**: 이 부분이 틀렸다, 왜냐하면…

### AI 에이전트 — 실행

- **분석**: 코드·문서 탐색, 원인 추적
- **계획**: 작업·실행계획서 작성
- **구현**: 코드·테스트 작성
- **문서**: 보고서·기술문서·커밋 메시지 작성
- **디버깅**: 로그 분석, 수정안 제시
- **반복**: 피드백 반영, 재시도

작업지시자가 코드를 직접 쓰지 않는 프로젝트에서도 위 목록의 왼쪽은 위임되지 않는다. 아키텍처 판단력이 아직 없다면 AI가 제안하고 작업지시자가 학습하며 승인하는 형태로 수행하되, 승인 주체는 바뀌지 않는다.

### 도메인 특수 항목

★도메인 지식 항목이 이 프로젝트에서 구체적으로 무엇을 뜻하는지 — **AI가 준비·분석까지만 하고 최종 판정은 작업지시자가 하는 대상**이 무엇인지 — 는 프로젝트마다 다르므로 `AGENTS.md`가 담당한다(§0). 그 항목은 `AGENTS.md`의 승인 목록에도 함께 오른다.

프로젝트가 무엇이든 다음은 변하지 않는다. **AI 에이전트는 검증 준비·자동 검사·초안 분석을 맡되 그 판정을 대신하지 않는다.** 산출물이 확률적이라면 한 번의 검토가 향후 모든 출력의 적합성을 보증하지 않는다는 점도 함께 적용된다.

## 2. 승인 없이 진행하지 않는 작업

"계획은 AI가 제안하되 승인은 사람이 한다"의 구체화. 아래 작업은 작업지시자의 명시적 승인 없이 진행하지 않는다.

1. **커밋·push**
2. **기술 스택·아키텍처 결정**
3. **프로젝트 데이터의 외부 전송·게시** (외부 API 호출·업로드로 저장소나 작업물의 내용이 밖으로 나가는 경우)
4. **파일 삭제·덮어쓰기** (특히 AI 에이전트가 직접 만들지 않은 파일)
5. **저장소 공개 범위 변경** (private → public)
6. **로드맵 단계 추가·삭제·순서 변경**

③이 막는 것은 **데이터가 밖으로 나가는 방향**이다. 기술 정보 조회(웹 검색·문서 열람)와 소프트웨어·모델 내려받기는 받아오는 방향이므로 승인 없이 한다 — 조사 범위를 승인 절차로 좁히면 검토가 로컬 지식에 갇혀 오히려 판단을 그르친다. 다만 **조회 요청 자체에 프로젝트 데이터를 실어 보내는 것**(검색어·프롬프트·이슈 본문에 작업물 내용을 넣는 것)은 ③에 해당하며, 금지선이 있는 프로젝트에서는 승인으로도 열리지 않는다.

이 여섯은 모든 프로젝트에 공통이다. **프로젝트 고유의 승인 항목과 금지선, 그리고 ①의 상설 승인 예외는 `AGENTS.md`의 같은 목록에 ⑦부터 이어 붙이며, 이 여섯과 동등하게 발효한다**(§0). 금지선은 승인 대상과 성질이 다르다 — 애초에 하지 않는 일이므로 승인으로 열리지 않는다.

**이 목록은 작업 루프 등급과 무관하게 발효한다**(§7.3 ①). 루프는 문서와 관문의 밀도를 정할 뿐 승인 대상을 줄이지 않는다. 설정 한 줄을 고치는 일은 복잡도상 경량 작업 루프에 속하지만, 그 한 줄이 ②에 걸리면 그 한 줄에 개별 승인이 붙는다.

## 3. 이 규약이 막는 것

이 규약은 "사람은 절대 생각을 멈추지 않는다"를 절차로 굳힌 것이다. 특히 §2의 승인 목록은 **AI 출력을 읽지 않고 수락하는 순간 = 바이브 코딩의 입구**를 막는 게이트다.

코드를 직접 쓰지 않는 작업지시자일수록 "그럴듯하게 동작하면 넘어가고 싶은" 유혹이 크다. 그리고 AI 산출물의 위험은 대부분 눈에 띄는 실패가 아니라 **그럴듯한 성공**의 형태로 온다 — 돌아가는 코드, 읽히는 문서, 통과하는 테스트인데 의도와 다른 것. 그것을 가려낼 수 있는 사람은 도메인을 아는 작업지시자뿐이므로, 규약은 그 사람이 반드시 멈춰 서는 지점을 미리 못 박아 둔다.

## 4. 문서 규칙

### 폴더 구조

타스크 흐름 7종과 지속 참조 `manual`을 `docs/` 바로 아래 평면 구조로 둔다. 독자 분류는 프로젝트 성격에 맞게 더한다.

| 폴더 | 담는 것 |
|---|---|
| `docs/orders/` | 오늘 할 일 (`yyyymmdd.md`) |
| `docs/plans/` | 작업·실행계획서 |
| `docs/working/` | 단계별 완료보고서 |
| `docs/report/` | 최종 결과보고서 |
| `docs/feedback/` | 사람의 검토·교정 기록 |
| `docs/tech/` | 기술적 발견 |
| `docs/troubleshootings/` | 문제·해결 경험담 |
| `docs/manual/` | 지속 참조 매뉴얼 — 작업 규칙의 정본 위치 |
| `docs/topics/` | 논의 스레드 — 구상·설계 논의 (`NNN_주제명/`) |
| `docs/design/` | 설계 문서 (독자 분류 — 필요 없으면 지운다) |
| `docs/domain/` | 도메인 지식 자료 (독자 분류 — 필요 없으면 지운다) |

빈 폴더는 `.gitkeep`으로 git에 등록한다.

### 파일·폴더 명명 규칙

- 일반 **MD 문서 파일명은 snake_case**. 단 도구·생태계가 규약으로 강제하는 문서(`AGENTS.md`·`CLAUDE.md`·`README.md` 등)는 예외.
- **폴더명은 항상 kebab-case**. 단 논의 스레드 폴더는 예외다(아래).
- **논의 스레드는 번호 접두를 쓰고 한글 이름을 허용한다** — 폴더 `NNN_주제명/`, 색인 `000_색인.md`, 글 `NN_제목.md`. 이 자리에 한해 폴더명 kebab-case와 파일명 snake_case의 예외다. 정렬과 인용은 번호가 담당하므로 이름은 사람이 읽기 쉬운 쪽을 택한다. 한글 파일명을 쓰는 저장소는 `core.precomposeunicode = true`를 설정한다.
- 코드·컴포넌트·설정파일 등 그 외 유형은 규칙 대상이 아니며 각 생태계 관례를 따른다.
- 타스크 산출물은 `task_{milestone}_{issue}` 골격을 쓴다.
  - 작업계획서: `task_m010_2.md`
  - 실행계획서: `task_m010_2_exec.md`
  - 단계별 완료보고서: `task_m010_2_stage1.md`
  - 최종 결과보고서: `task_m010_2_report.md`
- 파일명의 마일스톤은 소문자 `m{SemVer}`로 축약하고 생략된 patch는 `0`으로 보충한다(`v0.1` → `m010`, `v0.1.1` → `m011`). 이슈·마일스톤 표제는 버전 문자열을 그대로 쓴다.

### 문서 운용

- 새 문서는 분류에 맞는 폴더에 두고 **문서 위치 지도**(`docs/document_map.md`)를 갱신한다. 지도는 "무엇이 어디 있는가"의 안내이지 전 산출물의 장부가 아니다 — 모든 파일을 등재하지 않는다.
- **구상·설계 논의는 논의 스레드에 쌓는다**(아래 「논의 스레드」). 조사·검토·반론을 독립 문서로 흩지 않고 주제 폴더 안에 시간순으로 넣는다.
- **논의의 결론은 그 스레드의 색인이 정본이다.** 타스크 산출물은 결론을 다시 논증하지 않고 인용한다.
- 논의 스레드는 "어떻게 그렇게 정해졌는가"의 경과이고, 매뉴얼(`docs/manual/`)은 "지금 무엇이 유효한가"의 현재 상태 서술이다 — 서로 대체하지 않는다.
- **정본과 발췌본의 분담**은 §0을 따른다.
- **문서 형식**은 아래 「문서 형식」 절을 따른다.

### 논의 스레드

구상·설계 논의는 `docs/topics/` 아래 **주제 폴더 하나**에 모은다. 폴더가 곧 스레드이고, 번호 접두가 파일 정렬과 시간순을 일치시키므로 `ls` 결과가 그대로 논의 순서다.

```text
docs/topics/001_프로젝트_경쟁력/
├── 000_색인.md
├── 01_프로젝트_경쟁력_조사.md
└── 02_praat_7_성능_조사.md
```

**개설은 누구나, 승인 없이 한다.** 진입 문턱이 있으면 논의가 스레드 밖에서 벌어진다.

**색인(`000_색인.md`)** 은 다섯 절을 갖는다 — 무엇을 논의하는가 · 현재 논의 상태 · 미해결 · 오간 주장 · 결론. 「오간 주장」은 각 글의 주장을 옮겨 담은 표이며, 충돌하는 주장을 나란히 세우는 것이 이 표의 목적이다. 「결론」은 논의가 끝났을 때 채운다.

**글**은 머리에 `작성일 · 작성자 · 근거` 세 항목을 적고, 말미에 `## 주장` 절을 둔다. 주장은 번호 붙인 한 문장씩이며 "~하여야 한다" 꼴로 쓴다. 근거는 `실측`(우리 데이터) · `문헌`(외부 자료) · `추론` · `미확인` 중에서 고른다. 근거 표기를 두는 이유는, 같은 날짜의 두 글이 충돌할 때 그것을 가르는 정보가 최신성이 아니라 근거의 성격이기 때문이다.

- **반박도 하나의 글이다.** 두 줄짜리여도 새 번호를 받는다.
- **기존 글은 고치지 않는다.** 고치면 시간순이 무너지고 남이 이미 읽은 내용이 사라진다. 오탈자·링크 수정만 예외다.
- **번호는 재사용·재배열하지 않는다.** 동시에 같은 번호가 생기면 나중에 커밋되는 쪽이 다음 번호를 쓴다.
- **인용은 번호로 한다** — `001#02`, `01#주장2`. 파일명으로 걸면 제목을 고칠 때 깨진다.
- 주제가 겹치면 병합한다. 흡수되는 폴더는 색인만 `상태: 폐기(→ NNN에 흡수)`로 남기고 글을 옮긴다. **비운 번호는 재사용하지 않는다** — 과거 커밋과 인용이 계속 유효해야 한다.
- **폐기된 스레드는 폴더명 끝에 `--폐기됨`을 붙인다**(`012_주제명--폐기됨/`). 폴더 목록이 곧 스레드 목록이므로, 살아 있는 논의와 끝난 논의가 이름만 보고 갈라져야 한다. 색인 안의 `상태`만으로는 폴더를 하나씩 열어 봐야 알 수 있다. **구분자를 이중 하이픈으로 두는 것은 주제명이 언더스코어를 쓰기 때문이다** — `_폐기`로 적으면 주제명의 마지막 낱말과 같은 층위로 읽힌다. 번호와 주제명은 그대로 두고 접미만 더하며, 흡수처는 색인이 밝힌다. 인용은 번호로 하므로 폴더명이 바뀌어도 깨지지 않는다.

### 문서 형식

산문은 하드랩하지 않는다 — 문단은 줄바꿈 없이 한 줄로 쓰고, 줄바꿈은 문단·목록 항목·표 행의 경계에서만 넣는다.

그 밖의 형식 규칙은 린터가 강제할 수 있는 것만 둔다. 줄 길이가 문제로 보였던 사례는 대개 린터 규칙(`MD013`)의 기본값이 한국어 산문에 맞지 않았던 것이며, 그 경우 답은 폭을 다시 정하는 것이 아니라 린터 설정을 고치는 것이다. 프로젝트별 린트 규칙은 `.markdownlint.jsonc`에 둔다.

## 5. Git·브랜치 규칙

3층 브랜치 구조를 쓴다.

| 층 | 이름 | 보증하는 것 |
|---|---|---|
| 위 | `main` | 항상 배포 가능한 상태. 릴리스 시 태그 부여 |
| 가운데 | `devel` | 여러 타스크를 모아 통합·검증하는 완충 자리 |
| 아래 | `local/task{N}` | 한 타스크만 담는 격리된 작업 줄기 — 실패해도 여기서 끝난다 |

- **기본 브랜치는 `main`이다.**
- **흐름**: `local/task{N}` → (관련 타스크 묶어서) `devel` merge → (릴리스 시점) `main` merge (+태그).
- **세 작업 루프 모두 타스크 브랜치를 만든다**(§7). 아래층의 대표 이름은 `local/task{N}`이며 `N`은 GitHub Issue 번호다. 이슈를 채번하지 않는 경량 작업은 `local/{슬러그}`를 쓰고(예: `local/fix-toolbar-label`), 진행 중 상위 루프로 승격하면 이슈를 만든 뒤 `local/task{N}`으로 바꾼다(§7.6).
- **커밋 메시지**는 "무엇을·왜"를 요약한다. **이슈가 있으면 `Task #N:` 접두어를 붙이고, 없으면 붙이지 않는다.** 기준을 루프가 아니라 이슈 유무로 잡는 것은 브랜치 명명과 축을 맞추기 위해서다 — 승격·강등을 겪어도 규칙이 저절로 따라온다(§7.6).
- **커밋 메시지에 `closes #N`·`fixes #N` 등 이슈 자동 종료 키워드를 쓰지 않는다.** 이슈 종료는 반영 승인 뒤 원격 반영을 확인하고 나서 수행하는 **별도 절차**다(§7.5). 자동 종료 키워드는 push되는 순간 이슈를 닫아 그 순서를 앞지르며, 승인 전에 되돌려야 할 일을 만든다.
- 커밋은 마감 승인 뒤, push는 반영 승인 뒤에 한다(§2 ①, §7.5).
- 커밋 메시지 언어, 보존용 브랜치, 추적 예외 등 프로젝트 고유 규칙은 `AGENTS.md`에 둔다(§0).

## 6. 타스크·저장소 관리 규칙

### 원격 저장소와 공개 범위

원격 저장소 경로, 공개 범위(private/public), public 전환의 조건은 `AGENTS.md`가 담당한다(§0). 프로젝트와 무관하게 적용되는 것은 둘이다 — 공개 범위 변경은 승인 사항이며(§2 ⑤), **되돌릴 수 없는 행위이므로 실행 직전에 전체 커밋 이력을 감사한다.**

### 이슈·마일스톤

- **작업 루프 판정은 착수 시점에 한다**(§7). 판정 근거로 착수 시점에 답을 모르는 질문을 열거해 남긴다.
- 중량·일반 작업 루프의 타스크는 **GitHub Issue로 채번한다** — 이슈 번호가 곧 타스크 번호이자 브랜치 번호(`local/task{N}`)다. 경량 작업 루프는 채번하지 않는다. 경량마다 이슈를 만들면 이슈 목록이 잡음으로 찬다.
- GitHub 마일스톤과 orders 표제는 **버전 문자열로 명명한다**(`v0.1` 등, `M##` 축약 없음). 타스크 산출물 파일명에만 소문자 `m` 축약을 쓴다(§4). 로드맵 단계 이전·사이의 세분 마일스톤을 둘 수 있으며, 빈 미래 마일스톤은 미리 만들지 않는다.
- 현재 가동 중인 마일스톤은 진행에 따라 바뀌므로 `AGENTS.md`에 적는다(§0). 마일스톤 목록 자체의 정본은 `docs/manual/roadmap.md`이며, 단계의 추가·삭제·순서 변경은 승인 사항이다(§2 ⑥).

### 오늘 할 일 (orders)

- `docs/orders/yyyymmdd.md`로 하루를 여닫는다. 마일스톤 절 표제는 버전 문자열로 쓴다(예: `## v0.1 — …`).

### 금지선

금지선의 내용 — 어떤 정보·행위가 저장소에 들어가면 안 되고 대신 무엇을 쓰는지 — 은 프로젝트마다 다르므로 `AGENTS.md`가 담당한다(§0). 금지선을 두는 프로젝트에는 다음 둘이 공통으로 적용된다.

1. 금지선은 **어느 브랜치에도, 저장소가 private이어도** 예외가 없다. 커밋은 push되는 순간 원격에 영구히 남는다.
2. 금지선은 이슈(제목·본문·댓글·라벨)·마일스톤·`docs/orders/*`·커밋 메시지·코드 주석까지 **저장소에 들어가는 모든 텍스트**에 걸린다.

## 7. 타스크 진행 절차 — 세 작업 루프

### 7.1 분화의 축 — 복잡도

계획서 주도 루프는 서로 다른 두 가지 일을 동시에 한다. **승인 관문**은 잘못된 방향과 무단 변경을 막고, **단계 분할**은 AI 에이전트가 멀리 가서 길을 잃는 것을 막는다. 이 둘은 서로 다른 축을 따른다 — 관문은 위험을 따르고 단계는 복잡도를 따른다. 루프를 하나의 기준으로 가르려면 어느 축을 쓸지 정해야 하며, 본 규약은 **복잡도**를 축으로 삼는다.

위험을 축으로 삼지 않는 이유는 셋이다. 첫째, 위험 기준의 분류표는 §2 승인 목록의 복제가 된다 — 그 항목들은 이미 루프와 무관하게 개별 승인을 요구하므로, 같은 것을 루프 분류에서 다시 규정하면 규약이 길어질 뿐 새로 막아 주는 것이 없다. 둘째, 위험도는 착수 시점에 판정하기 어렵다. 셋째, 위험이 낮으면서 어려운 작업을 가벼운 쪽으로 흘려보낸다.

복잡도를 「복잡하다」로 두면 협상 대상이 되므로 조작적 정의를 둔다. 지표는 **착수 시점에 답을 모르는 질문의 수**다. 단계를 나누는 이유는 중간에 확인해야 하기 때문이고, 확인이 필요한 이유는 모르기 때문이므로, 이 지표는 단계 분할의 근거와 직접 일치한다.

### 7.2 세 작업 루프

| 작업 루프 | 부르는 조건 — 착수 시점의 미지 | 문서 | 관문 |
|---|---|---|---|
| **중량 작업 루프** | 미지가 많다. 중간 결과를 봐야 다음 단계가 정해지고, 결과가 설계를 뒤집을 수 있다 | 작업계획서 + 실행계획서 + 단계별 완료보고서 + 최종 결과보고서 | 작업계획 승인 · 실행계획 승인 · 단계별 승인 N회 · 마감 승인 · 반영 승인 |
| **일반 작업 루프** | 미지가 적다. 구현하면서 밝혀지고, 밝혀져도 방향이 바뀌지 않는다 | 작업계획서 1종(무엇·왜·어떻게) + 최종 결과보고서 | 계획 승인 · 마감 승인 · 반영 승인 |
| **경량 작업 루프** | 미지가 없다. 무엇을 어떻게 할지 이미 확정되어 있고, 결과를 보지 않아도 다음 수가 정해진다 | 계획서 없음 — 완료 시 orders 한 줄 | 마감 승인 · 반영 승인 |

세 루프는 **이슈 채번 여부**, **요구하는 문서**, **중간 승인 관문의 밀도**에서 갈린다. 앞의 둘은 있고 없음이고, 셋째는 정도의 차이다 — 중량은 실행계획 승인과 단계별 승인 N회를 중간에 두고, 일반은 계획 승인 하나로 줄이며, 경량은 중간 관문 없이 마감으로 직행한다. 브랜치 명명과 커밋 접두어는 이슈 유무에서 파생된다(§5). 마감 2관문(§7.5)과 §2 승인 목록은 세 루프에서 동일하다.

세칙은 다음과 같다.

- **파일명**: 실행계획서(`_exec.md`)와 단계별 완료보고서(`_stage{N}.md`)는 중량 작업 루프 전용이다. 일반 작업 루프의 계획서는 `task_{milestone}_{issue}.md` 한 개이며 무엇·왜에 더해 어떻게까지 담는다.
- **orders**: 세 루프 모두 완료 시 해당 날짜의 orders에 기록한다. 경량은 한 줄로 족하다.

### 7.3 세 안전장치

1. **위험은 축이 아니라 하한선이다.** §2의 승인 목록은 루프 등급과 무관하게 발효한다. 위험 항목이 걸렸다고 루프를 통째로 올리지 않고, 걸린 그 항목의 관문만 얹는다.
2. **판정이 애매하면 상위 루프가 기본값이며, 승격은 자유롭고 강등은 작업지시자만 한다.** 착수 시점에 미지가 없다고 보았으나 진행 중 답을 모르는 질문이 드러나면 그 자리에서 상위 루프로 올린다. 반대 방향은 작업지시자의 결정 없이는 하지 않는다.
3. **단계 수는 중간 확인이 필요한 지점의 수로 정한다.** 형식상의 최소 단계 수를 두지 않는다. 단계가 하나뿐인 타스크는 예외가 아니라 정상 적용이다.

### 7.4 루프별 절차

세 루프에 공통으로 걸리는 것은 다음과 같다. §2의 승인 목록은 루프 등급과 무관하게 발효한다. 루프 판정은 착수 시점에 하고 판정 근거로 답을 모르는 질문을 열거해 남긴다. `main` 통합·태그, 저장소 공개 범위 변경, 외부 서비스 전송은 어느 루프에서도 별도 관문이다.

#### 중량 작업 루프

1. **이슈 등록** — GitHub Issue로 채번하고 범위·마일스톤을 정한다. 본문에 루프 판정과 모르는 질문 목록을 적는다.
2. **타스크 브랜치 생성** — `local/task{N}`으로 전환한다.
3. **작업계획서 작성 → 〈작업계획 승인〉** — `task_{milestone}_{issue}.md`에 무엇을·왜 할지 쓴다.
4. **실행계획서 작성 → 〈실행계획 승인〉** — `task_{milestone}_{issue}_exec.md`에 어떻게 할지 쓴다. 단계는 중간 확인이 필요한 지점의 수만큼 나눈다. 사람 검증이 필요하면 자동 검증과 작업지시자 판정의 대상·방법·기준을 구분한다.
5. **단계 구현·검증** — 승인된 현재 단계만 실행하고 계획한 자동 검증을 수행한다.
6. **단계별 완료보고 → 〈단계 승인〉** — `task_{milestone}_{issue}_stage{i}.md`에 계획 대비 결과와 검증을 기록한다. 작업지시자가 필요한 사람 검증을 수행하고 승인·수정·반려한다.
7. **단계 커밋 뒤 5로 되돌아간다.** 남은 단계가 없으면 8로 간다.
8. **최종 결과보고서와 orders 작성** — `task_{milestone}_{issue}_report.md`에 전체 계획 대비 결과를 기록하고 완료일 orders를 갱신한다.
9. **〈마감 승인〉** — 커밋 → `devel` 통합 → 회귀 검증.
10. **〈반영 승인〉** — push → 원격 반영 확인 → Issue 종료 → 타스크 브랜치 삭제.

#### 일반 작업 루프

1. **이슈 등록** — 위와 같다.
2. **타스크 브랜치 생성** — `local/task{N}`으로 전환한다.
3. **계획서 작성 → 〈계획 승인〉** — 한 문서에 무엇을·왜에 더해 어떻게까지 쓴다. 변경할 파일, 구현 순서, 검증 방법, 비목표를 담는다. 단계로 나누지 않고 실행계획서를 별도로 쓰지 않는다.
4. **구현·검증** — 계획서 범위를 한 번에 구현하고 자동 검증을 수행한다. 사람 검증이 필요하면 환경과 시나리오를 준비한다.
5. **최종 결과보고서와 orders 작성** — 계획 대비 결과, 검증 결과, 남은 한계를 기록한다.
6. **〈마감 승인〉** — 작업지시자가 최종 diff와 보고서를 검토하고 필요한 사람 검증을 수행해 판정한다. 승인 시 커밋 → `devel` 통합 → 회귀 검증. 반려되면 같은 루프 안에서 고쳐 재검증·재보고한다.
7. **〈반영 승인〉** — push → 원격 확인 → Issue 종료 → 브랜치 삭제.

#### 경량 작업 루프

1. **착수** — 이슈를 채번하지 않고 `local/{슬러그}` 브랜치를 만들어 전환한다. 범위는 작업지시 자체에 이미 확정되어 있다. 계획서를 쓰지 않는다.
2. **구현·검증** — 해당하는 자동 검증만 수행한다(§8).
3. **〈마감 승인〉** — 작업지시자가 결과를 확인한다. 승인 시 변경과 orders 한 줄을 한 커밋으로 묶고, `devel`에 통합한 뒤 회귀 검증을 수행한다.
4. **〈반영 승인〉** — push → 원격 확인 → 브랜치 삭제.

관문 수는 중량이 `4 + 단계 수`, 일반이 3, 경량이 2다.

### 7.5 마감 2관문

마감 절차를 로컬과 원격의 경계에서 한 번만 자른다.

| 관문 | 승인 시 수행 |
|---|---|
| **마감 승인** | 커밋 → `devel` 통합 → 회귀 검증 |
| **반영 승인** | push → 원격 반영 확인 → Issue 종료 → 타스크 브랜치 삭제 |

**두 관문의 내용은 세 루프에서 동일하다.** 중량·일반 작업 루프에서는 최종 결과보고서 승인이 곧 마감 승인이고, 경량 작업 루프에서는 결과 확인이 그 자리를 대신할 뿐 수행하는 동작은 같다. 세 루프 모두 타스크 브랜치를 쓰므로 `devel` 통합이 빠지는 예외가 없다.

**Issue 종료는 반영 승인 뒤 원격 반영을 확인하고 나서 사람 또는 AI가 명시적으로 수행하는 동작이다** — 커밋 메시지의 자동 종료 키워드로 대신하지 않는다(§5).

`main` 통합·태그, 저장소 공개 범위 변경, 외부 서비스 전송은 묶음 밖의 별도 관문으로 둔다. 묶음에 정지 조건이나 예외 규칙을 덧붙이지 않는다 — 커밋·통합·회귀 검증에서 오류가 나면 그 자리에서 판단해 대응하고 보고한다.

### 7.6 승격·강등 시의 처리

두 원칙이 이 절을 지배한다. 첫째, **식별자는 한 번 정해지면 타스크가 끝날 때까지 바뀌지 않는다** — 유일한 예외가 경량에서 이슈가 처음 생기는 순간의 브랜치 이름 변경이다. 둘째, **승격은 산출물을 더하고 강등은 남은 산출물만 줄인다** — 강등이 이미 만든 이슈·브랜치·문서를 지우지 않는다.

**승격** — 진행 중 새 질문이 드러났을 때 AI 에이전트가 그 자리에서 수행한다.

| 전이 | Issue | 브랜치 | 문서 |
|---|---|---|---|
| 경량 → 일반 | 새로 채번한다. 본문에 승격 근거로 드러난 질문과 이미 만든 변경의 현황을 적는다 | `git branch -m local/{슬러그} local/task{N}` | 계획서를 새로 쓴다. 이미 만든 변경은 계획서의 현황으로 흡수한다 |
| 경량 → 중량 | 위와 같다 | 위와 같다 | 작업계획서와 실행계획서를 차례로 쓴다 |
| 일반 → 중량 | 그대로 | 그대로 | 기존 계획서를 작업계획서로 삼고 실행계획서를 새로 쓴다 |

**강등** — 작업지시자만 결정한다.

| 전이 | Issue | 브랜치 | 문서 |
|---|---|---|---|
| 중량 → 일반 | 그대로 둔다 | 그대로 둔다 | 이미 쓴 실행계획서·단계별 완료보고서를 지우지 않는다. 실행계획서에 강등 사실과 이후 처리를 덧붙이고, 남은 범위는 단계로 나누지 않는다 |
| 일반 → 경량 | 그대로 둔다. 닫지 않는다 | 그대로 둔다. 슬러그로 되돌리지 않는다 | 계획서를 남기고, 최종 결과보고서 대신 orders 한 줄로 마감한다 |

일반 → 경량에서 이슈를 닫거나 브랜치 이름을 되돌리지 않는 이유는, 경량의 「이슈 없음」이 새로 만들지 않는다는 뜻이지 있으면 없앤다는 뜻이 아니기 때문이다. 이미 발행된 번호를 회수하면 커밋과 문서에 남은 참조가 끊긴다.

경계 사례는 셋이다. **승격 전 커밋의 접두어**는 소급해 다시 쓰지 않고 승격 시점 이후의 커밋부터 붙인다 — 이력을 고쳐 얻는 것은 형식 일관성뿐인데 되돌림 비용이 있다. **이미 통합·push된 작업의 승격**은 승격이 아니라 새 타스크다. **원격에 올라간 경량 브랜치**는 경량이 반영 승인 전까지 push되지 않으므로 보통 생기지 않으며, 예외적으로 생기면 새 타스크로 다룬다.

### 7.7 승인과 커밋의 경계

- 작업계획서 승인은 실행계획서 작성으로, 실행계획서 승인은 첫 단계 실행으로 넘어갈 권한이다. 일반 작업 루프의 계획 승인은 곧바로 구현으로 넘어갈 권한이다.
- 단계별 완료보고서 승인은 해당 단계 소스와 보고서의 커밋 승인까지 포함한다. 마감 승인·반영 승인은 포함하지 않는다.
- 수정 요청이나 반려를 받으면 같은 단계에서 수정·재검증·재보고하고 다시 승인받는다.
- 마감 승인 전에는 완료 기록·통합을 수행하지 않고, 반영 승인 전에는 push·Issue 종료·브랜치 삭제를 수행하지 않는다.

### 7.8 사람 검증이 필요한 타스크

- 중량 작업 루프는 실행계획서에서, 일반 작업 루프는 계획서에서 자동 검증과 작업지시자 검증의 대상·방법·판정 기준을 구분한다. 경량 작업 루프는 마감 승인의 결과 확인이 그 자리다.
- AI 에이전트는 검증 가능한 환경과 시나리오를 준비하고 자동 검증 결과를 보고한다. 시각적 품질이나 도메인 적합성처럼 사람 판단이 필요한 결과는 작업지시자가 판정한다.
- §1 도메인 특수 항목에 걸리는 변경은 별도 절차로 분리하지 않고 해당 타스크의 검증 단계에서 다룬다.

### 7.9 발효

본 절은 프로젝트 개시 시점부터 발효한다. 개정할 때는 개정일과 **어느 타스크부터 적용하는지**를 이 절에 적는다.

발효의 실질은 작동 발췌본 `AGENTS.md`가 갱신되는 시점이다 — 세션 컨텍스트에 로드되는 것은 작동본이고 본 정본은 로드되지 않으므로, AI 에이전트의 실제 행동은 작동본이 바뀔 때 바뀐다(§0 ②).

## 8. 검증·품질 규칙

검증은 두 종류로 갈리며, 이 구분은 프로젝트와 무관하다.

- **자동 검증** — AI 에이전트가 수행하고 결과를 보고한다. 린트·빌드·테스트·회귀 검증이 여기 속한다.
- **작업지시자 판정** — 시각적 품질이나 도메인 적합성처럼 사람만 내릴 수 있는 판단. AI 에이전트는 환경과 시나리오를 준비할 뿐 판정을 대신하지 않는다(§1·§7.8).

계획서는 이 둘의 **대상·방법·판정 기준을 구분해** 적는다(§7.8). 자동 검증을 통과했다는 사실이 작업지시자 판정을 대신하지 않는다.

**「자동 검증」이 구체적으로 무슨 명령인지는 스택마다 다르므로 `AGENTS.md`가 담당한다**(§0). 그 자리가 비어 있으면 세 작업 루프의 검증 단계가 작동하지 않는다.

## 11. 적용 범위와 유예 모듈

협업 문서는 독자에 따라 세 모듈로 갈라지며, 본 규약은 그중 **A**만 다룬다. B·C는 발효 조건이 올 때 도입한다.

| 모듈 | 성격 | 발효 조건 |
|---|---|---|
| **A. 프로젝트 운용 규칙** (본 문서) | 작업지시자–AI 에이전트 내부 작업 규칙 | **지금** |
| **B. 외부 선언** | 도구의 성격·방법론·한계의 대외 천명 (`README.md` 등) | 저장소 public 전환 시 |
| **C. 기여자 행동 규칙** | 외부 기여자의 행동 규약 (`CONTRIBUTING.md` 등) | 외부 기여자 합류 시 |

발효 조건이 이 기본과 다르면 `AGENTS.md`에 적는다. B·C가 발효되면 그 대외 문서도 본 규약에 절을 두고, 대외 문서 자체는 발췌·요약본으로 작성한다(§0).
