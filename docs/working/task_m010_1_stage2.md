## 갈래 A — 본 라벨링

착수했다. 범위 선언은 아직 받지 못했다.

**밀도 참고값** — 파일럿(첫 1분)에서 대상자 발성 분당 4.6개. 도입부 1분에서 나온 값이라 근거가 약하다.

**권고한 범위** — 표본 단위를 분이 아니라 **대상자 발성 개수**로 잡는다. 비율 추정의 정밀도가 개수에 달렸기 때문이다(`n`=30이면 95% 신뢰구간 반폭 ±10.7%p, `n`=100이면 ±5.9%p, 참값 0.9 근처). 지금 답할 물음이 「망가졌나 아닌가」 수준이므로 **약 100개**면 충분하다고 보았고, 밀도 3~6개/분을 폭으로 잡으면 **20~30분**이다. 3~5분 블록 5~8개로 회기의 서로 다른 대목에 흩기를 권했다 — `covered` 가 배열이라 흩어진 구간이 스키마 그대로 담기고, 한 대목만 보면 선택 편향이 그 대목의 성질에 통째로 실린다.

**어디를 고를지와 최종 분량은 작업지시자가 정한다**(`AGENTS.md` §2 ⑧).

## 갈래 B — 도구 개선

작업지시자 판정을 세 차례 더 받아 고쳤다. 단계 1의 판정 1~3회차에 이어진다.

| 커밋 | 무엇을 |
|---|---|
| `25ac00b` | 1초 점프, 미세 조정 모드, 키 처리 결함 둘, 들은 범위 삭제 |
| `847edc7` | 미세 조정 다듬기를 Shift 에 기대지 않게 함 |
| `e796faa` | 제3자 발성 범주(`other_voice`), `schema_version` 2 |

**미세 조정 모드**(`A`) — 실시간으로 누르거나 급히 짚은 구간의 경계를 뒤에서 다듬는다. `[`·`]` 로 경계 지점 사이를 옮기고, `,`·`.` 로 0.05초씩 다듬으며, `Space` 는 그 구간만 재생하고 끝에서 멈춘 뒤 재생 머리를 선택 지점으로 되돌린다. 단계 1에서 「경계 시각을 다듬는 기능은 넣지 않는다」고 했던 결정을 뒤집은 것이다 — 파형을 보고 짚어도 실시간으로 누른 구간에는 반응 지연이 남고, 작업지시자가 필요하다고 판정했다.

**키 처리 결함 둘.** 실제 Chrome 에서 재현해 원인을 확인했다.

- Space 한 번에 `play@0.00` → `pause@0.00` 이 났다. 핸들러가 버블 단계에 있어 `<video>` 의 기본 컨트롤이 먼저 토글하고 우리가 되돌린 것이다. 캡처 단계로 옮기고 우리가 쓰는 키는 `stopPropagation` 으로 막았다. 화살표 키에도 같은 이중 동작이 있었다.
- 파일을 고른 뒤 포커스가 파일 칸에 남아 `INPUT` 가드가 모든 단축키를 삼켰다. 선택 직후 `blur` 하고 가드를 글자를 넣는 칸에만 걸었다.

**단축키를 물리 키(`e.code`)로 가르게 바꿨다.** `e.key` 는 자판 배열과 입력기에 휘둘려 한글 입력 상태에서 `a` 가 `ㅁ` 으로 온다. 뒤이어 작업지시자가 미세 조정 모드에서 `<`·`>` 가 1초 점프로 동작한다고 보고했는데, 같은 물리 키에 Shift 로만 갈리는 구조여서 Shift 가 실려 오지 않으면 새어 나간다. 확장과 헤드리스 Chrome 양쪽에서 재현되지 않아 **원인을 좁히는 대신 의존 자체를 없앴다** — 모드 안에서 `,`·`.` 를 다듬기로 받고 1초 점프를 두지 않는다.

**들은 범위 삭제.** 지울 길이 아예 없었다. 목록의 삭제 버튼과 `Shift`+`C`(재생 머리가 든 범위)를 두고, 범위를 지워 바깥에 남은 라벨이 생기면 내보내기에서 경고하게 했다.

**자동 검증** — 헤드리스 Chrome 을 CDP 로 구동해 9개 항목 47개 확인. 매 변경마다 전부 통과. 검증 스크립트는 작업지시자 판단으로 저장소에 넣지 않고 스크래치패드에 둔다(Chrome 확장이 연결되어 있으므로).

## 옆방 음성 혼입 — 범주를 다시 열었다

작업지시자가 라벨링 중 보고했다. **옆방 회기의 음성이 참여자와 유사한 강도로, 거의 회기 내내 새어 들어온다.**

사람의 말이지만 이 회기의 참여자가 아니므로 세 범주 어디에도 들어가지 않고, 무라벨의 뜻(「사람의 발성이 아니다」)을 거짓으로 만들었다. **동결 대상이므로 규칙대로 멈추고 보고했고**, 승인을 받아 고쳤다.

- `other_voice` 를 **`4` 에 붙였다.** `3` 보류는 이미 손에 익었으므로 뜻을 바꾸지 않았다 — 자리를 밀면 손에 익은 대로 눌러 잘못 들어간다.
- 이미 만든 라벨은 범주 문자열로 저장되므로 **그대로 보존된다.** 마이그레이션이 필요 없다.
- 무라벨의 뜻을 **「이 회기 참여자의 발성이 아니다」**로 정정하고 `schema_version` 을 2로 올렸다.
- 혼입이 잦은 조건의 표시 우선순위를 절차에 적었다 — **참여자 발성과 겹치는 제3자는 반드시**, 단독은 생략 가능, 밀도 측정용으로 한 블록만 빠짐없이.

논의 스레드 `008_옆방_음성_혼입` 을 열었다. 요지는 **2화자 가정이 깨졌을 가능성**이다 — `002` 의 화자 판별 실패 원인으로 임베딩 품질과 발화 길이가 지목되어 왔으나(`003#01`·`003#02`), 애초에 화자가 둘이 아니었다면 그 방향은 빗나간 것이다.

## 아키텍처 재검토 — `003#05`

작업지시자가 발상을 전환했다. **회기 외부 음성은 대상자 음성과 굳이 구분되지 않아도 된다. 단, 임상가 음성과 구분된다는 전제 하에서.** 이 도구의 목적이 탐색 속도이지 정밀 검출이 아니기 때문이다.

구성은 임상가 개인 마이크 별도 녹음 → iPhone 녹화본과 싱크 → 채널 에너지비로 임상가 판별 → 임상가 트랙 전사를 탐색 색인으로 → 대상자 후보는 「임상가가 아닌 유성 구간」이며 오염 허용.

이어 「외부 음성이 없어도 현행 방식이 원활히 가르는가」를 물었고, 코드 구조로 따진 답은 **그렇다고 말할 수 없다**였다. 논증과 두 방식 비교는 **`docs/topics/003_화자_판별_방식/05_임상가_마이크_아키텍처와_현행_방식_비교.md` 가 정본**이며, 여기 옮겨 적지 않는다.

**이 타스크에 미치는 영향** — 바꿀 것이 없다. 라벨링은 그대로 계속한다. 다만 용도의 무게가 옮겨 간다.

| 라벨의 쓸모 | 새 설계에서 |
|---|---|
| 대상자 발성의 검출 재현율 | 그대로 핵심 — 설계와 무관한 토대다 |
| 제3자 혼입 밀도·겹침 비율 | **값어치 상승** — 「후보에 섞이는 양이 감당되는가」(`05#3`)를 가른다 |
| F0·비발성 표지 채점(`04`) | 그대로 유효 |
| 깨끗한 구간에서의 현행 화자 정확도 | **새로 생긴 쓸모** — 「마이크가 필요한가 튜닝으로 될 일인가」를 가른다 |
| k-means 화자 판별 튜닝 | 불필요해진다 — 그 경로를 폴백으로 강등하는 방향이므로 |

**아키텍처 결정은 아직 승인되지 않았다**(작업 규약 §2 ②). 스레드에 논증만 쌓았다.
